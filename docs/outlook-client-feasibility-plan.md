# Outlook client feasibility plan

## Objective

Determine whether a local, read-only Python client can list, search, and retrieve
mail from the signed-in user's Outlook mailbox by using the authentication and
backend calls available to the current Outlook Web client, without a new Entra
application registration or additional tenant consent. An authenticated browser
page is a useful probe, but the target is a reusable local connector that can
later serve the web UI and MCP tools.

This document is an investigation plan, not a claim that Outlook's private
endpoints or standalone authentication have been verified.

## Public baseline

- [Microsoft Graph message listing](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0) documents mailbox and folder listing with OData query parameters. The [folder API](https://learn.microsoft.com/en-us/graph/api/user-list-mailfolders) covers folder enumeration, and [message delta](https://learn.microsoft.com/en-us/graph/delta-query-messages) covers incremental changes per folder.
- Graph's mail APIs require delegated mail permissions such as `Mail.ReadBasic` or `Mail.Read`, depending on the data requested. Whether this account can obtain those permissions without new consent is an open question; [Entra consent policy](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/user-admin-consent-overview) is controlled by the tenant.
- The older `outlook.office.com/api/v2.0` Outlook REST API is [deprecated](https://learn.microsoft.com/en-us/outlook/rest/compare-graph). Do not treat its historical routes as evidence of what the current Outlook Web app uses.

## Investigation sequence

### 1. Map the current Outlook Web calls

With the user signed in to `https://outlook.office.com/mail/`, inspect requests
generated by these read-only actions: load Inbox, change folder, load the next
page, open one message, and run one search. Record only the method, host, route
shape, parameter names, response structure, pagination markers, and auth
mechanism. Do not record token or cookie values, message bodies, subjects, or
personal identifiers in the research notes.

Check whether the app calls Graph, Exchange/OWA private endpoints, or both.
Inspect downloaded JavaScript only to explain observed routes and parameters;
do not infer a working contract from bundle strings alone.

### 2. Prove read access in the signed-in page

Reissue a small, read-only request from the Outlook page's JavaScript context
using its existing session. Test one folder page with a small count, then one
message by ID. Confirm the response is usable and that the request does not
change `isRead` or any other mailbox state. If the page uses cookies, request
headers, or anti-forgery values, record their *roles* without copying values.

### 3. Test a standalone local connector

Find the resource audience and sign-in method actually used for mail access.
Compare the Outlook Web client's non-secret identity and requested scopes with
the token audience and permissions accepted by the observed mail endpoint.
Test whether an equivalent public-client sign-in can be used locally without
new registration or consent; do not assume a Teams token is valid for mail.
Try a local Python request with an app-owned MSAL session and read-only scopes
that are already available to this account. Keep Teams and Outlook credentials
separate. Determine whether the request succeeds without a new app registration,
consent prompt, browser profile dependency, or copied session secret. Repeat
after token expiry to test silent renewal. Treat a browser-only success and a
standalone Python success as different outcomes.

Stop this path if tenant policy denies access or the required authentication
cannot be obtained through the user's normal sign-in. Document the observed
failure rather than attempting to bypass it.

### 4. Measure useful mailbox operations

For every working path, test and document:

| Operation | Questions to answer |
|---|---|
| List folders | Are nested, shared, archive, and hidden folders included? |
| List latest messages | Is descending received time guaranteed? What page size and cursor are supported? |
| Filter by date and folder | Which conditions run on the server, and are range boundaries inclusive? |
| Search | Does the server search subject, body, sender, recipients, and attachments? Can it limit scope to a folder or date range? |
| Read message | Are HTML and plain text bodies, thread IDs, sender/recipient fields, and attachments available? |
| Incremental sync | Is there a change token or delta route, and what does it cover? |

Use a few known messages and two or more pages to verify sort order, duplicates,
continuations, and the difference between message and conversation/thread views.
Keep tests read-only and check unread state before and after the probes.

### 5. Decide and build a minimal proof of concept

- **Standalone viable:** a local Python connector can authenticate, refresh, and
  perform the needed reads. Implement `list_folders`, `list_messages` with
  bounded paging and filters, `get_message`, and the verified search operations.
  Start with latest messages by count across the mailbox, then folder and date
  filters, then search and classification support.
- **Browser-only viable:** calls work inside Outlook Web but cannot be renewed
  or replayed locally. Document the browser dependency and decide whether a
  browser bridge is acceptable before building a lasting client.
- **Not viable under current access:** the route requires unavailable consent,
  tenant approval, or session material that cannot be safely reused. Record the
  exact blocking condition and stop.

The proof of concept should return structured message metadata and short
excerpts, with explicit coverage limits. Do not persist mailbox contents or
build an index until storage, retention, and deletion behavior are specified.

## Deliverables

1. A route matrix listing observed endpoints, methods, accepted parameters,
   response fields, pagination, credential audience, and confidence level.
2. A reproducible read-only probe showing browser-context and standalone-local
   results separately, without secrets or private mail content in its logs.
3. A decision on whether the local UI and future MCP server can share an
   Outlook connector, plus a small implementation scope for the next milestone.
